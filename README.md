# Group Chat Court

An AI-powered party game for a whole group chat. File a case about a harmless
friend-group disagreement, summon the accused to defend themselves, seat
everyone else as the jury, and let a comedy judge hand down a verdict nobody
asked for — on the record, against their priors, and sometimes against the
jury's wishes.

> **Entertainment only.** Verdicts are generated by a language model from two
> unverified accounts. They establish nothing about what actually happened, and
> they are not legal advice or dispute resolution.

```
File a case → the accused defends themselves → the group chat votes
          → the judge rules (and may overrule the jury) → it goes on their record
```

Four things make it a game rather than a form:

* **The courtroom.** Every case is a live group chat. The plaintiff, the accused,
  the jury and Judge Byte all talk in it: the charge opens as a statement, the
  defence answers, the judge reads the priors aloud, jurors argue and shout
  **OBJECTION!**, and the judge rules on the spot.
* **The jury.** Everyone else in the chat votes guilty or not guilty from a
  second link, and **nobody sees the ruling until they have voted**. A vote is a
  commitment, so the reveal is worth something.
* **The record.** Every verdict lands on a permanent rap sheet — convictions,
  acquittals, guilty streaks — scoped to one court. The judge is handed those
  priors and reads them out before sentencing.
* **The reveal.** The verdict arrives as a short staged sequence rather than a
  wall of text, and the best outcome in the game has its own banner: the judge
  overruling the room.

## How it fits together

```
Flutter / web (creator)       Browser (defendant · juror · viewer)
      │                                      │
      │  Bearer JWT                          │  capability token in the URL
      ▼                                      ▼
┌──────────────────────── FastAPI /api/v1 ────────────────────────┐
│  cases · invites · jury · verdict · share · public · reports    │
│  ownership checks · rate limits · safety screening              │
└───────────────┬───────────────────────────────┬─────────────────┘
                │ claims a job (conditional UPDATE)
                ▼                               ▼
         verdict_jobs table  ──────────►  worker ──► LLMProvider
                                                     (mock | anthropic)
```

Three independent capabilities, deliberately never shared:

| | Invitation link | Jury link | Public verdict link |
|---|---|---|---|
| Created | with the case | with the case | only when the creator opts in |
| Audience | the accused, alone | the whole group chat | anyone |
| Grants | filing one defense | one vote, then the ruling | reading the sanitized verdict |
| Revoked by | deleting the case | deleting the case | `DELETE /cases/{id}/share` or deleting the case |

Revoking one never affects the others. Only SHA-256 hashes are stored, so a
database dump yields no working links.

A juror is identified by a random key their own browser generates, hashed
before storage. It is enough to stop a refresh from stuffing the ballot box and
not enough to identify anyone from the database — and `UNIQUE (case_id,
voter_key)` is what actually enforces one ballot per juror, not the UI.

## The courtroom (websocket)

One socket, `WS /api/v1/ws/room`. The **first frame authenticates**, so tokens
never appear in a URL (where they would land in access logs):

```jsonc
{"type":"auth","kind":"creator","case_id":"…","token":"<jwt>"}   // the plaintiff
{"type":"auth","kind":"defendant","token":"inv_…"}               // the accused
{"type":"auth","kind":"juror","token":"jry_…","voter":"<device key>","name":"Priya"}
```

Every failure is the same `invalid_link` error. After that:

| Client → server | Meaning |
|---|---|
| `{"type":"say","body":"…"}` | speak (≤ 280 chars) |
| `{"type":"object"}` | object; the judge rules instantly (2 per person per case) |
| `{"type":"hide","id":"…"}` | the plaintiff clears someone else's line |

| Server → client | Meaning |
|---|---|
| `welcome` | your seat, plus the last 100 messages |
| `message` / `hidden` | a new line / a line to take down |
| `presence` | how many are here now |
| `roster` | the jury box: who is in the room, in order, and whether each has **voted** (never which way) |
| `case` | the case status changed (`ready`, `completed`, …) |
| `error` | a refusal, for you alone: `blocked`, `slow_down`, `too_long`, `capped`, `closed` |

**Messages live in the database, not in the socket.** Each is a row with a
per-case position `n`, unique per case. A connection is a reader that tails that
log: woken instantly when the same process writes, and by a 1.5 s timer
otherwise. That is what lets the verdict worker — a separate process with no
access to any socket — still speak in the room, and it means no Redis is needed
to run more than one API instance. "Here now" is counted per process.

**What the room never carries:** the ruling. Judge Byte announces that a
decision exists (`meta.verdict_ready`); the verdict itself is still only released
by the vote-gated REST endpoint. A vote is announced ("Mia has cast a vote") but
never which way.

**Keeping order.** Chat is the one place a stranger holding a link can address a
named person, so: every line goes through the safety screen plus a slur/pile-on
filter and is **rejected before it is stored**, not hidden afterwards; speakers
are paced (0.9 s between lines, 15 a minute, 80 a case for jurors); the plaintiff
can clear a line; anyone can mute someone locally; the judge's lines cannot be
cleared. Objection rulings are comedy, not adjudication — deterministic from the
message id, so a retry never flips one.

## Design

The look is taken from **"Digitizing US courtroom trials"** by Tejas Sarvankar
(https://dribbble.com/shots/11802833-Digitizing-US-courtroom-trials-UX-UI): a
bright, airy courtroom. A white canvas with faint washes of yellow, blue and
green behind it; grey **trays** holding large rounded **squircle** participant
tiles with presence dots; folder-tab labels (Plaintiff / Defense); a numbered
**Jury Box**; "Court Trial · 17867" cards with a courthouse icon and a pill;
window-chrome dots on panels; soft, broad shadows; and saturated **pill
buttons whose colour carries meaning**:

| Colour | Sampled | Means |
|---|---|---|
| Blue | `#1773E4` | go / join / primary |
| Green | `#7AE86F` | allow / yes / not guilty (deeper `#1C9D46` when used as text) |
| Red | `#D9524C` | deny / guilty / objection |
| Orange | `#FF7441` | later / both guilty / overruled |

Palette values were sampled from the reference image; fills keep its hue, and
text on a fill is chosen for contrast (white on blue and red, ink on green and
orange). The typeface is **Open Sans** (light for display, bold for names).

The tokens live in two places and must be changed together: the `:root` blocks
in `web/src/styles.css`, and `CourtColors`/`CourtPalette` in
`mobile/lib/core/theme.dart`. Both clients are **light by default**; the web app
adds a dark variant under `prefers-color-scheme: dark`, and the mobile app has an
**Appearance** setting (Light / Dark / System) that defaults to Light, so a phone
that happens to be in dark mode does not silently change what the app is.

## Case lifecycle

```
draft ──► awaiting_defense ──► ready ──► generating ──► completed
                 │                │           │
                 │                │           └──► failed ──┐
                 ▼                ▼                         │
              expired          expired        (retry, safely)
```

* `claim_generation` is a conditional `UPDATE … WHERE status IN ('ready','failed')`.
  Two concurrent requests cannot both win, so a case can never get two verdicts.
* The queue is the `verdict_jobs` **table**, not an in-process task. A restart
  mid-generation leaves a row whose lock goes stale and is reclaimed.
* Expiry is applied lazily on read/write, so no case can be read or written
  without first being checked.
* The LLM never writes database state. It returns a validated value object and
  the service decides what happens.

## Authentication

`AUTH_PROVIDER` selects the strategy; the rest of the app only ever sees a
resolved `User`, so swapping providers touches one file (`app/security/auth.py`).

* **`dev`** (default) — `POST /auth/dev-login` issues an HS256 JWT for a
  device-generated subject. No password, no email. The endpoint 404s when
  `ENVIRONMENT` is `staging` or `production`.
* **`jwks`** — verifies RS256 tokens from a managed identity provider. Set
  `JWKS_URL` and `JWKS_AUDIENCE`. The first authenticated call provisions the
  local user record from the token's `sub`.

To move to a managed provider: set `AUTH_PROVIDER=jwks`, point `JWKS_URL` at the
issuer, and replace the Flutter sign-in screen's `devLogin` call with that
provider's SDK. Nothing else changes.

## Configuring the LLM

| Variable | Default | Notes |
|---|---|---|
| `LLM_PROVIDER` | `mock` | `mock`, `anthropic`, `gemini` or `ollama` |
| `ANTHROPIC_API_KEY` | — | required only for `anthropic` |
| `LLM_MODEL` | `claude-opus-5-5` | |
| `LLM_EFFORT` | `low` | a one-paragraph verdict does not need deep reasoning |
| `LLM_TIMEOUT_SECONDS` | `45` | per attempt |
| `LLM_MAX_ATTEMPTS` | `3` | retries within one job attempt |
| `LLM_MAX_ATTEMPTS_PER_CASE` | `5` | hard spend ceiling per case |

The real provider uses structured output (`messages.parse` with
`output_format=VerdictOutput`), so malformed model output cannot reach the
database. Refusals arrive as `stop_reason == "refusal"` and are **not** retried —
the same input would only be declined again at the same cost. SDK-level retries
are disabled so every attempt is counted and capped by `VerdictService`.

**Gemini** (`LLM_PROVIDER=gemini`) answers in a few seconds and needs no GPU:

| Variable | Default | Notes |
|---|---|---|
| `GEMINI_API_KEY` | — | required; goes in `.env` (gitignored), sent as a header, never in a URL |
| `GEMINI_MODEL` | `gemini-2.5-flash` | its own setting, so `LLM_MODEL` can stay pointed at another provider |
| `GEMINI_THINKING_BUDGET` | `0` | `0` turns "thinking" off, which is most of the latency |

Check a setup end to end before anyone files a case — it times a real verdict
and prints the result, never the key:

```bash
cd backend && set -a && . ../.env && set +a
.venv/bin/python scripts/try_provider.py
```

A local `ollama` model is fine for offline work but slow on a modest GPU: a 9B
model that does not fit in VRAM spills onto the CPU and takes 20-40 s a verdict,
and Ollama unloads an idle model after 5 minutes (`OLLAMA_KEEP_ALIVE` holds it).

**Never commit an API key.** `.env` is gitignored; `.env.example` has no secrets.

## Safety

Safety does not rely on the system prompt alone.

1. **Before generation** — `screen_text` matches phrase-level patterns for
   violence, abuse, self-harm, harassment, crime, hate, real legal disputes and
   medical crises. A match means the model never sees the case; the creator gets
   a stored, serious, non-comedic answer instead of a stuck case.
2. **The prompt** (`app/prompts/verdict_prompt.py`, versioned, `PROMPT_VERSION`
   stored on every verdict) treats both submissions as unverified claims, wraps
   them in `<accusation>` / `<defense>` tags as *data not instructions*, forbids
   jokes about protected traits, and requires an insufficient-evidence verdict
   when the accounts conflict.
3. **After generation** — `review_output` rejects banned content and catches a
   model that joked about material it was told to decline. Rejected output is
   replaced, never stored.

Priors and the jury are given to the judge as *facts supplied by us*, in their
own tags, separate from the two untrusted submissions — and the prompt is
explicit that a record is a running joke, never grounds for conviction. A case
blocked by the pre-screen or by output review touches nobody's record: a refusal
is not a trial.

## Sharing and Open Graph

* `GET /api/v1/public/verdicts/{token}` — sanitized DTO, built field-by-field
  from an allowlist. Adding a private column to `Case` or `Verdict` cannot widen
  it by accident.
* `…/card.svg` — the share image, rendered from **one reusable SVG template**
  with text substituted. No per-case image model, no headless browser in the
  request path. All text is HTML-escaped.
* `…/preview` — a minimal HTML shell carrying Open Graph and Twitter card tags,
  for crawlers (which do not execute JavaScript, so the SPA cannot supply them).
  Humans are bounced to the SPA. Point your share links here, or have your CDN
  serve it to known crawler user-agents.

> **Social platforms cache preview metadata aggressively.** Facebook, X,
> LinkedIn and iMessage will keep serving a stale title and image for hours or
> days after a change, and a *revoked* link may still show its old preview in a
> chat thread even though the page itself now 404s. Use each platform's debugger
> (e.g. Facebook's Sharing Debugger) to force a re-scrape when iterating.
> If you need a PNG instead of SVG for a platform that rejects SVG `og:image`,
> render `card.svg` with a headless browser or `resvg` in a background job and
> cache the result — keep it out of the request path.

## Testing

No test needs a paid API key, network access, or a running database.

```bash
cd backend && .venv/bin/python -m pytest        # 165 tests
cd web     && npm test                          # 72 tests
cd mobile  && flutter test                      # 118 tests
```

The backend suite runs on SQLite by default so it needs no infrastructure. To
run it against PostgreSQL (recommended before a release — it is the production
dialect):

```bash
cd backend
DATABASE_URL="postgresql+psycopg://gcc:gcc@localhost:5433/gcc" \
ENVIRONMENT=test RATE_LIMIT_ENABLED=false RUN_JOBS_INLINE=false \
JWT_SECRET=test-secret .venv/bin/python -m pytest
```

What is covered: case creation and validation, ownership and authentication,
invitation token validation, defense submission, duplicate-submission rejection
(at both the application *and* the database-constraint level), expired
invitations, every state transition, concurrent verdict requests, LLM schema
validation, timeout/retry/refusal handling, job durability across a simulated
worker death, public-verdict privacy, link revocation, case deletion, rate
limits, serious-content handling, and prompt-injection tagging.

For the courtroom: the first frame must be auth, a bad credential gets the same
generic error however it is bad, messages never reach another case's room, refused
lines are never stored, pacing and per-case ceilings hold, objections are capped
and always ruled on, only the plaintiff can clear and never the judge, a vote is
announced without its direction, the room hears that a verdict exists but never
what it is, a message written by another process still arrives, and simultaneous
writers never share a position. The web and Flutter clients are tested against a
fake socket: they authenticate in the first frame, reconnect with growing backoff,
treat a dead link as final, and never double the transcript when history replays.

For the jury and the records specifically: one ballot per juror (enforced by the
database, not the UI), the tally staying hidden until *this* juror has voted,
the verdict being refused to a juror who never voted, voting closing the moment
the court rules, convictions and streaks accumulating correctly for every
verdict kind, records never crossing between two courts, and `jury_overruled`
being true only when the judge actually landed opposite a jury that reached a
majority.

## Database

```bash
cd backend
.venv/bin/alembic upgrade head        # apply
.venv/bin/alembic downgrade -1        # roll back one
.venv/bin/alembic revision --autogenerate -m "describe the change"
.venv/bin/alembic check               # fails if models have drifted
```

The migration URL comes from `DATABASE_URL`, never from `alembic.ini`, so no
credentials live in a committed file.

| Table | Notes |
|---|---|
| `users` | unique `auth_subject` |
| `cases` | soft delete, expiry, share- and jury-token hashes, generation attempt counter |
| `participants` | unique `(case_id, role)`; holds the invite token hash |
| `jury_votes` | **unique `(case_id, voter_key)`** — the database is what guarantees one ballot per juror |
| `offenders` | unique `(owner_id, slug)` — one criminal record per nickname per court |
| `chat_messages` | **unique `(case_id, n)`** — the room's log; the database orders it |
| `submissions` | **unique `participant_id`** — the database is what guarantees one defense |
| `verdicts` | unique `case_id`; JSONB `result` plus `model_version` / `prompt_version` |
| `verdict_jobs` | unique `case_id`; the durable queue |
| `reports` | abuse reports |

Deletes cascade from `users` → `cases` → `participants` → `submissions`, and
from `cases` → `jury_votes`. A deleted `offenders` row sets the case's record
columns to NULL rather than taking the case with it.

## Deployment

The three services deploy independently.

**Database** — any managed PostgreSQL 14+. Run `alembic upgrade head` as a
release step before the new API version starts.

**API** — build `backend/Dockerfile` and run
`uvicorn app.main:app --host 0.0.0.0 --port 8000` behind TLS. Set at minimum:
`ENVIRONMENT=production`, a 32-byte random `JWT_SECRET`, `DATABASE_URL`,
`WEB_BASE_URL`, `API_BASE_URL`, `AUTH_PROVIDER=jwks` + `JWKS_URL`, and
`LLM_PROVIDER=anthropic` + `ANTHROPIC_API_KEY` from your secret manager.

**Worker** — the same image, running `python -m app.services.job_runner`. Set
`RUN_JOBS_INLINE=false` on the API so it only enqueues. Several workers can run
concurrently; claiming is a conditional `UPDATE`, and a dead worker's job is
reclaimed after `JOB_STALE_SECONDS`.

**Websockets** — the proxy in front of the API must allow connection upgrades
(`Upgrade`/`Connection` headers) and an idle timeout comfortably over 30 s; the
server sends a ping every 25 s. Behind TLS the client connects with `wss://`,
derived from `API_BASE_URL`/`VITE_API_BASE_URL`.

**Web** — `npm run build` produces a static `dist/`; serve it from any CDN with
an SPA fallback to `index.html`. `VITE_API_BASE_URL` is inlined at build time,
so it must be an address the *browser* can reach.

**Mobile** — `flutter build apk` / `flutter build ipa`, passing
`--dart-define=API_BASE_URL=https://api.yourdomain`.

### Before a public launch

The MVP is built for a private beta. Three things are deliberately scoped for
that and should be revisited first:

1. **Rate limiting is in-process.** `app/security/rate_limit.py` holds counters
   in memory, so limits are per-instance. Move the counter to Redis before
   running more than one API instance.
2. **`EXTRA_CORS_ORIGINS` must be tight.** Browsers treat `localhost` and
   `127.0.0.1` as different origins; list exactly what you need and no wildcards.
3. **The safety screen is a denylist.** It is a floor, not a ceiling. Pair it
   with human review of the `reports` table before opening sign-ups.
